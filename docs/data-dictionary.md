# Complaint Management Data Pipeline — Data Dictionary

## 1. Purpose

This document defines the structure, meaning, validation rules, and relationships of the datasets generated by the Complaint Management Data Pipeline.

The pipeline follows a parent-first generation approach. Master entities are generated before dependent transaction and workflow records so that relationships can be validated using primary and foreign keys.

---

## 2. Entity Overview

| Entity | Description | Primary Key |
|---|---|---|
| Customer | Synthetic customer master data | customer_id |
| Product | Synthetic product master data | product_id |
| Category | Complaint category reference data | category_id |
| Order | Customer product orders | order_id |
| Complaint | Customer complaints linked to orders/products | complaint_id |
| Assignment | Team and agent assigned to a complaint | assignment_id |
| SLA Clock | SLA tracking information for a complaint | sla_id |
| Complaint Message | Customer/system communication history | message_id |
| Status Event | Immutable complaint lifecycle events | event_id |
| Resolution | Final action taken on a complaint | resolution_id |
| Survey | Post-resolution customer feedback | survey_id |
| Ground Truth | Deliberate known anomalies | anomaly_id |

# 14. Ground Truth

**File:** `data/ground_truth/ground_truth.csv`

Ground truth contains intentionally injected anomalies used to demonstrate validation and exception detection.

| Field | Type | Required | Description |
|---|---|---|---|
| anomaly_id | string | Yes | Unique anomaly identifier |
| complaint_id | string | Yes | Affected complaint |
| issue_type | string | Yes | Type of deliberate anomaly |
| description | string | Yes | Explanation of expected issue |

The pipeline contains six deliberate anomaly types:

1. `COMPLAINT_WITHOUT_CUSTOMER`
2. `RESOLUTION_BEFORE_COMPLAINT`
3. `SLA_PAUSE_ERROR`
4. `REPEAT_ISSUE_NOT_LINKED`
5. `SAFETY_WRONG_QUEUE`
6. `SURVEY_BEFORE_CLOSURE`

Ground-truth records are maintained separately from normal input/output data so that known exceptions can be validated without becoming normal business data.

```text
Customer
   │
   ├── Order
   │      │
   │      └── Product
   │
   └── Complaint
          │
          ├── Product
          ├── Order (optional)
          ├── Assignment
          ├── SLA Clock
          ├── Complaint Messages
          ├── Status Events
          ├── Resolution
          └── Survey
```

The primary traceability path is:

```text
Customer
  → Order
  → Complaint
  → Assignment
  → SLA Clock
  → Messages / Status Events
  → Resolution
  → Survey
```

# 16. Data Quality Principles

The pipeline validates the following principles:

1. Primary keys must be unique and non-null.
2. Foreign keys must reference valid parent records unless the record is an intentional ground-truth anomaly.
3. Enumerated fields must contain allowed values.
4. Derived values must be calculated from source records.
5. Lifecycle events must maintain chronological consistency.
6. Resolutions must occur only after complaint creation.
7. Surveys must normally occur after complaint closure.
8. SLA values must correspond to complaint priority.
9. Known deliberate anomalies must be independently identifiable.
10. The same seed must reproduce identical datasets.
